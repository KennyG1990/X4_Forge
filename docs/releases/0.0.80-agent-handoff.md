## Changes relevant to mod-building agents

- Root `ui.xml` is UI XML, with manifest/schema and registration checks. Imported UI
  source and registrations are preserved; conflicting generated output is refused.
- Imported node/link IDs derive from file-scoped source identity. Reimport retains
  existing IDs and layout when the match is unambiguous; ambiguous duplicates do not
  silently inherit another node's identity. Consumers must use returned IDs rather
  than reconstructing old filename, numeric or time-based prefixes.
- Deployment validates its captured artifact inputs, compares the reviewed identities
  and checks source/corpus/target consistency before writes. A separate old validation
  response is not authorization to ship newly edited bytes.
- Exact warning reviews can be reused when their evidence remains unchanged. Each
  deployment retains the original reviewer/reason and the reuse record. New, known,
  resolved, invalidated and revoked reviews are distinguishable.
- The bounded validation matrix covers the reported script-property/property-access,
  nested-selector, schema, listener/registration, large-Lua tail and UI-manifest cases.
  Dynamic or unsupported analysis remains explicitly unverified. See the
  [C04 scope matrix](../testing/claude-C04-gotcha-matrix.md) for the exact rules and limits.
- Incremental validation reuses unchanged Lua/XML/schema/reference work with dependency
  invalidation. [C05 evidence](../testing/claude-C05-incremental.json) records parity and
  measured workloads; it does not establish a universal speedup for every mod.
- Compile/artifact responses distinguish produced output, validation failure and
  unavailable evidence. The supported compile capability is `workspace.compile@2`.
- Mod-specific API responses identify their addressed source. Shared source coordination
  serializes cooperating Forge writes across local sidecars; status exposes its state.

## Address the intended instance, workspace and mod

Discover the current Forge address and capability contract. Preserve the authenticated
client's `x-client-id` and `x-workspace-id` headers; do not reuse another client's active
workspace or a remembered port as identity. Workspace-bound keys can deploy only the mod
identified by their addressed workspace. Import/select the intended mod there first.

Deployment requires exactly one explicit target: `path` or `workspace`. It never defaults
to whichever workspace happens to be active. Request fields and types are checked;
unknown or malformed fields are not a supported compatibility fallback.

`modId`, `sourceHash` and `sourceHashScope` describe the addressed subject. Respect the
scope: a workspace head, validation inputs, artifact inputs and pasted-log bytes are
different identities. Collection/environment responses need not invent a mod identity;
unresolved subjects may contain null identities. A release artifact's folder selector
can differ from the validated `content.xml` identity; inspect `modIdScope`, `sourceIdentity`
and `validatedSource` where returned. None proves what the running game has loaded.

## Preview, review, then apply

POST `/api/agent/deploy-verify` with the explicit source folder:

```json
{"path":"your_mod_folder","dryRun":true}
```

Inspect the returned validation evidence, coverage gaps, review state and deployment
effect. Apply using the four identities from that exact preview:

```js
{
  path: "your_mod_folder",
  expectedModId: preview.modId,
  expectedSourceHash: preview.sourceHash,
  expectedArtifactHash: preview.artifactHash,
  expectedBindingHash: preview.bindingHash
}
```

`/api/agent/deploy` is an alias with the same guards. For the inline-workspace form,
use the same explicit workspace in preview and apply instead of `path`. If using
`autoReimport` or `deployFormat`, preserve those choices across the sequence.

Do not submit saved pre-update bindings. Validator/dependency/corpus changes can invalidate
them even when mod files have not changed. Source, artifact, target or addressed-workspace
changes also require a fresh preview. `SOURCE_STALE`, `DEPLOY_WORKSPACE_MOD_MISMATCH`,
`DEPLOY_IDENTITY_MISMATCH` and `DEPLOY_SOURCE_CHANGED` are refusals, not permission to omit
the expected fields or copy files around the Forge.

An HTTP 200 is not sufficient evidence of deployment: inspect the response verdict and
stages. A blocked mod-finding response includes `blockingFindings` with code/file/line/message
and an `acceptanceRequest` template. Review each finding; an empty reason in that template
is deliberately insufficient. Safety/integrity failures cannot be accepted.

## Reviewed warnings and exact finding acceptance

A deploy-authorized agent may accept an exact finding with its reason:

```js
acceptances: [{
  findingId: reviewedFinding.findingId,
  bindingHash: preview.bindingHash,
  reason: "Specific evidence supporting this exact decision"
}]
```

The server records the authenticated actor. A client cannot choose an approver by adding
an identity to the body. Do not blanket-accept all findings. Errors never inherit automatic
warning approval, and acceptance cannot turn unavailable coverage into a passed check.

List current reviews through a fresh deploy preview's `validation.review.warningReviews`.
Automatic reuse is warning-only and depends on the same canonical source/mod, finding
context, validation-input bytes, validator/corpus and coverage evidence. A stable finding
ID is not an assurance that an edited source still has an approved review. Changed evidence
or revoked review requires a fresh decision; original approval and reuse remain auditable.

To revoke a listed review, POST `/api/agent/warning-reviews/revoke` with:

```js
{
  receiptId: originalReviewReceiptId,
  reviewScopeHash: currentReviewScopeHash,
  reason: "Why this review should no longer be reused"
}
```

Use the original receipt ID and `scopeHash` from the same preview review list. Revocation
requires deploy permission and a nonblank single-line reason of at most 512 characters.
It changes review history, not mod/game files. Obtain a fresh preview afterward.

Read `validation.outcome`, `validation.clean`, `acceptanceRecords`, `deployRecord` and
`baselinePromotion` after apply. Accepted findings or unavailable checks produce a
qualified result; they are not clean validation or in-game verification. Preserve the
returned receipt IDs with the mod build record instead of relying on console color alone.

## Coordination and dependency failures

GET `/api/agent/status` includes `sourceCoordination` and the addressed workspace/source.
The coordinator uses a dedicated local native-SQLite registry to serialize cooperating
Forge processes writing the same canonical resources. Claims cover actual work and cleanup,
including after an HTTP disconnect. Do not delete the registry or infer that an old-looking
claim is safe to steal. Queue, lost-ownership and unavailable-registry responses are explicit
refusals; inspect status and recover the affected instance before retrying.

This lock cannot control unrelated editors, older Forge versions or writes outside the
cooperating protocol. External changes still depend on source-hash refusal. Dev instances
must have an explicit private coordination directory distinct from production.

Validator identity includes the installed parsing dependencies and their locked metadata.
Missing/mismatched package metadata or dependency resolution outside the packaged app can
raise `VALIDATOR_FINGERPRINT_UNAVAILABLE`. Missing native SQLite or an unusable coordination
registry can prevent protected writes. These are Forge environment failures, not mod findings
to accept. A partial installation must be repaired; copying an old approval does not repair it.
