# 0.0.79: UI manifests and trustworthy deployment

This release fixes UI-manifest classification/validation and deployment evidence.
It does not claim to resolve every item in the broader Claude review, complete the
B119 editor, reload the running game, or deploy any user's mod.

## What changed

- Root `ui.xml` is UI XML, not Lua. The game's addon schema and registration checks
  cover it. Imported registrations and source bytes survive import/compile/reopen;
  conflicting generated output is refused instead of replacing imported source.
- Mod findings and unavailable Forge checks are distinct. Unavailable checks alone
  do not block deployment, but the result remains qualified and cannot become a
  last-green validation baseline.
- Deploy-authorized agents can accept exact findings with a reason. The authenticated
  actor, finding identity, source/rule binding, and reason are stored durably and
  linked from the deployment record. The client cannot invent the actor identity.
- Deployment is bound to the reviewed mod, semantic source, all artifact bytes,
  validator/rules, and target. Changes require a fresh preview, not a stale approval.

## Required API sequence

Use the currently discovered Forge address and the existing workspace-bound agent
key. Preserve the `x-client-id` and `x-workspace-id` addressing headers.

First POST `/api/agent/deploy-verify`:

```json
{"path":"your_mod_folder","dryRun":true}
```

Inspect its validation evidence. To apply, POST the same path with these fields
copied from that response (not old saved values):

```js
{
  path: "your_mod_folder",
  expectedModId: preview.modId,
  expectedSourceHash: preview.sourceHash,
  expectedArtifactHash: preview.artifactHash,
  expectedBindingHash: preview.bindingHash
}
```

For a finding you explicitly reviewed and accept, add only that finding:

```js
acceptances: [{
  findingId: reviewedFinding.findingId,
  bindingHash: preview.bindingHash,
  reason: "Specific evidence explaining why this finding is accepted"
}]
```

Do not automatically accept all errors. No acceptance is needed merely because a
check was unavailable. Read `validation.outcome`, `acceptanceRecords`, `deployRecord`,
and `baselinePromotion` in the result. A successful byte deployment is not proof of
in-game execution or experience. `/api/agent/deploy` enforces the same binding checks.
A 409 means preview/review again; do not retry by omitting identity fields.
