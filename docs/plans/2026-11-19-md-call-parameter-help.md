# Contextual Mission Director call parameters

Source and private host verified under [#74](https://github.com/KennyG1990/X4_Forge/issues/74) and its [parameter contract #82](https://github.com/KennyG1990/X4_Forge/issues/82). Source baseline `d02ee561ea0a9e755841ce57a966c4653c994108`. Packaged installation remains a release gate.

Forge already resolves authored cue and library references and validates direct parameter names. Its signature reader in `src/lib/cueLineage.ts` distinguishes known empty signatures from unavailable ones. The validator's direct and composed callers use the same declaration identity. The extension gives generic schema completion and hover with `xmlCursorContext`, but a search of the committed extension found no signature help for a resolved library call. Move the smallest existing signature reader to an extension-safe shared dependency and keep its current validation consumers.

X4 9.00 `libraries/md.xsd` allows direct `<param name="…" value="…"/>` arguments on `<run_actions>` and `<cue ref="…">`. Their accepted library purposes differ. `<include_actions>` runs in the caller's context and has no supplied parameter children. Library declarations expose a name, optional default value and documentation comment. Reuse the existing purpose decisions and keep the existing validation severities.

## Acceptance

- Resolve an exact authored library call in one opened mod using unsaved caller and provider buffers. Display the declaration and its direct parameter names with required or default information. When editing an existing named argument, select the parameter by exact spelling.
- Offer declared names at the direct `param/@name` cursor. Cover both XML quote styles and unfinished text without requiring the entire caller buffer to parse. Reuse the editor's lexical cursor context. Recover only a bounded local edit when finding same-file declarations past an incomplete tag. Leave document bytes unchanged.
- Return no guessed signature for an ambiguous, dynamic, wrong-purpose, foreign-namespace, malformed or effective patch target. Distinguish an exact known empty signature. Verify that `<include_actions>` never offers `<param>` names. Keep cancellation and changed-buffer checks coherent with existing navigation.
- Compare the same exact cue and action fixtures with the installed CodeSense 1.2 language interface. Check exact-case different names, direct versus nested arguments, required and defaulted declarations, incomplete values, and unsaved provider changes. Use X4 schema and the existing [action witness](https://github.com/KennyG1990/X4_Forge/issues/82#issuecomment-6771223421) for game rules.
- Require focused source tests, the existing argument and purpose checks, native provider execution and a real isolated host before public delivery. Record cursor ranges, results and the exact loaded controller. Roll back the bounded editor provider and shared reader extraction together if existing validation regresses.

The current API completion and hover endpoints accept the current file buffer. Agent access to unsaved sibling declarations needs explicit project authority under [#19](https://github.com/KennyG1990/X4_Forge/issues/19). Effective patch composition, engine behavior changes and multi-mod lookup stay in their existing work records.

## Reconciled implementation order

1. Move the existing signature and argument readers from `src/lib/cueLineage.ts` to `shared/mdDeclarationResolution.ts`. Keep the current exports as aliases for validators. Run the existing cue and effective argument checks before adding editor presentation fields.
2. Use `shared/xmlMarkup.ts` and the editor's cursor context to identify a direct call or argument. Keep original source offsets. Test incomplete attributes, single quotes, opaque markup, and unrelated descendants before wiring suggestions.
3. Resolve the declaration with the existing editor sibling snapshot. Project the same exact signature into the native assistance provider. Verify closed and open providers, active named arguments, version changes and cancellation.

The installed CodeSense 1.2.0 LSP benchmark returned ten successful cases on two indexed scratch scripts. It reported required and defaulted parameters for `run_actions` and `cue ref`, selected the matching active argument, and offered only unsupplied names at the next child. Exact XML replacement ranges stayed available inside an unfinished quoted name. The `include_actions` control returned no parameter signature. The receipt retains the fixtures and responses. [Public comparator](https://marketplace.visualstudio.com/items?itemName=X4DevTools.x4codesense).

Forge uses its shared validator signature, argument, purpose and declaration rules. The existing completion provider gives a resolved direct parameter-name value the exact replacement range. The native signature shows default values, the active argument, documentation and the declaration location. Completion puts required arguments first and retains declaration order among arguments with the same priority. Signature display keeps declaration order. Ordinary XML exits early into its existing completion path. No capability-map delta for the released package.

The private candidate passed the root and extension TypeScript configurations, the focused editor checks, 40 navigation checks, 29 commit-orchestration checks, 35 cue-lineage and 113 cross-file checks, and the existing effective include and MD context suites. The ten captured CodeSense cases matched the Forge signature labels and active argument indexes. The six cases with captured name completions matched the labels, insertion text and exact source ranges. The focused editor controls are part of the ordinary commit gate.

Required-first sorting beat reversed declaration order. The saved fixture hashes stayed identical and the Forge sidecar discovery directory stayed empty.
