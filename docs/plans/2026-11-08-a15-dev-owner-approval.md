## Private host contract

The launcher supplies `X4_FORGE_PROJECT_CHECK_OWNER_POLICY` as a JSON environment value. Its exact fields are `version` (1), `workspaceId`, `actorId`, `modId`, `sourceRoot`, `interpreterPath`, `interpreterDependencies`, `runtime`, and `credential`. The runtime pins `pythonPath`, `pythonSha256`, `workerPath`, `workerSha256`, `launcherSha256`, and `systemRoot`. The credential pins `ownerId`, `origin`, `credentialId`, `userHandle`, and `publicKeySpki` as base64url SPKI DER for P-256. The private key stays with the owner's credential. Use a fixed `PORT` matching the exact `http://localhost:<PORT>` origin, an explicit `STUDIO_API_TOKEN`, the isolated Dev roots, and `X4_FORGE_PROJECT_CHECK_RUNS=1`. A dotenv file cannot opt the host into owner mode.

The review response contains the setup and runtime facts for the operator to inspect before asking the device for an assertion. Send the returned `reviewId` and the assertion as `proof` to confirm, with the same origin. The assertion fields are `type`, `id`, `userHandle`, `clientDataJSON`, `authenticatorData`, and `signature`. Challenges are short-lived and single-use. The backend verifies the exact challenge, origin, credential signature, user presence and user verification. [WebAuthn assertion verification](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion).

## AAR

Keep the signed fixture and exact receipt through native apply in the same replay. Review found that the usual Studio token, writable path configuration and raw-command escape could undermine an owner boundary. The isolated owner profile now locks those paths and checks its scope before startup state writes. Review also found that a rejected confirmation could strand a challenge slot. Confirmations now reserve their slot until they settle and discard the nonce even when refused. Pinning the owner and runtime at launch protects against accidental changes in the product. Real device provisioning and a clear review on screen still need their own proof.
