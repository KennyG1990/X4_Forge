API CONTRACT / PROOF BOUNDARY
- All three runtime-control endpoints require an explicit workspace selected with x-workspace-id and the authenticated client. Status GET and preview POST {} allow read/write/deploy; reload POST requires deploy. Preview generates files in its response only. Its debugger read can persist bounded ingestion/audit state.
- Reload requires exactly requestId (32 lower hex), command (refreshmd or reloadui), expectedModId, expectedWorkspaceHash, expectedSessionId, reason. The hash identifies the addressed workspace model; it does NOT certify current disk or game bytes. Existing successful deploy baseline is required. Actual reload completion remains unverified even with matching invocation report.
- A request produces a durable authorization receipt before delivery. It records authenticated actor and reason; receipt outcome describes authorization, not game execution. HTTP 202 with queued-awaiting-evidence is only delivery evidence. Status may later report invocation-observed, failed, expired, session-changed, or delivery-unconfirmed. There is no keyboard fallback.
- Log evidence is an attributed mod report, not cryptographically authenticated game telemetry. Save detection covers own-mod FORGE-LIFECYCLE instrumentation only. A missing/rotated log or uninstrumented save cannot be inferred to have a known save identity. Current-segment coverage is exposed separately.
- Companion supports only a private fixed file outbox, expires in 15 seconds, and persists consumption before invoking. Missing io/os/scheduler/command/registration/logging capability refuses. Its callback uses the existing Helper scheduler; no replacement of onUpdate.
- No user/player UI changed. Backend/fixture proof is applicable now. Installed private backend proof is required; native game reload/save-load proof is deliberately deferred under the explicit no-game-command batch boundary. Neither stable Forge nor the running game will be restarted.
